GETTING STARTED

1. Account Creation & Editions

What you choose on day one, and why it matters later.

Snowflake is a cloud data platform — it runs on top of AWS, Azure or GCP, but you never manage servers. You pick a cloud, a region, and an edition. The trial gives 30 days and $400 of credits, which is enough to practise everything in this course.

Editions — know the differences

EditionWhat it adds
StandardCore platform, 1 day Time Travel, all basic SQL features.
EnterpriseUp to 90 days Time Travel, multi-cluster warehouses, materialised views, search optimisation, column-level security (masking).
Business CriticalStronger encryption, HIPAA/PCI compliance, failover across regions.
Virtual Private (VPS)Completely isolated Snowflake environment — banks and defence use this.
Interview point

Masking policies and multi-cluster warehouses need Enterprise edition at minimum. If someone asks why a masking policy failed on their account, edition is the first thing to check.

Ways to connect

  • Snowsight — the web UI, where you will spend most of your time.
  • SnowSQL — the command-line client, needed for loading local files with PUT.
  • Connectors — Python, JDBC, ODBC, Spark, and the dbt adapter.

SECURITY MODEL

2. Roles & Users

Snowflake's whole security model is role-based. Get this right and the rest follows.

A user never owns permissions directly. Permissions are granted to roles, and roles are granted to users. Roles can also be granted to other roles, which builds a hierarchy where a senior role automatically inherits everything below it.

The system-defined roles

RoleWhat it is for
ORGADMINManages the organisation and creates accounts.
ACCOUNTADMINTop of the tree — billing, account settings. Give it to two or three people only, never for daily work.
SECURITYADMINManages users, roles and grants globally.
USERADMINCreates users and roles (but not global grants).
SYSADMINCreates databases, schemas, warehouses. Your custom roles should roll up here.
PUBLICEvery user gets it automatically. Anything granted here is visible to everybody.
A CUSTOM ROLE, DONE PROPERLYUSE ROLE USERADMIN;
CREATE ROLE R_ANALYST;
CREATE USER rahul PASSWORD='Temp@123' DEFAULT_ROLE=R_ANALYST MUST_CHANGE_PASSWORD=TRUE;
GRANT ROLE R_ANALYST TO USER rahul;

USE ROLE SYSADMIN;
GRANT USAGE ON WAREHOUSE COMPUTE_WH TO ROLE R_ANALYST;
GRANT USAGE ON DATABASE SALES_DB TO ROLE R_ANALYST;
GRANT USAGE ON SCHEMA SALES_DB.RAW TO ROLE R_ANALYST;
GRANT SELECT ON ALL TABLES IN SCHEMA SALES_DB.RAW TO ROLE R_ANALYST;

-- and for tables created in future, otherwise new tables are invisible
GRANT SELECT ON FUTURE TABLES IN SCHEMA SALES_DB.RAW TO ROLE R_ANALYST;

-- roll the custom role up so SYSADMIN can manage it
GRANT ROLE R_ANALYST TO ROLE SYSADMIN;
The mistake everyone makes once

Granting SELECT on all tables, then wondering why the analyst cannot see the table created yesterday. ON ALL is a snapshot of what exists now; ON FUTURE covers what comes later. You usually need both.

Remember the hierarchy

Think of an office. USERADMIN is HR issuing ID cards. SYSADMIN is the facilities manager who owns the rooms. ACCOUNTADMIN is the owner who also sees the electricity bill. Nobody does daily work wearing the owner's badge.

Two useful commands when access breaks: SHOW GRANTS TO ROLE R_ANALYST; and SHOW GRANTS ON TABLE SALES_DB.RAW.ORDERS;. Also remember a role needs USAGE on the database and the schema before any table grant works — three levels, and people forget the middle one.

HOW SNOWFLAKE IS BUILT

3. Architecture

The single most asked interview topic. Learn it as three layers.

Cloud Services→ Query Processing (Compute)→ Database Storage

Cloud services layer

The brain. Authentication, access control, the optimiser, metadata, transaction management, and the result cache. You do not pay for it separately in normal use.

Query processing layer

Virtual warehouses — the muscle. Each is an independent MPP cluster. Many warehouses can read the same data at the same time without slowing each other down.

Storage layer

Your data, held in the cloud provider's object storage as compressed, columnar micro-partitions. You cannot see the files; Snowflake manages them.

Shared disk vs shared nothing vs Snowflake

ModelHow it worksWeakness
Shared diskMany compute nodes, one common storage.Storage becomes the bottleneck; nodes fight over it.
Shared nothingEach node owns its slice of data and its own disk.Scaling means physically redistributing data; compute and storage must grow together.
Snowflake (hybrid)Central shared storage, plus shared-nothing compute clusters that cache what they need locally.Takes the benefits of both: scale compute and storage independently.
Say this sentence and the question is answered

Snowflake separates storage from compute. Storage is shared and central; compute is independent clusters. That is why the finance team's heavy query cannot slow down the loading pipeline, and why you can resize a warehouse without touching a single byte of data.

Micro-partitions

Snowflake automatically splits table data into micro-partitions of roughly 50–500 MB of uncompressed data, stored columnar. For each one it keeps metadata — the min and max of every column, distinct counts, null counts.

When you filter on a column, the optimiser reads that metadata and skips partitions that cannot possibly match. This is partition pruning, and it is the reason a well-filtered query on a billion-row table can finish in seconds.

Picture for micro-partitions

A library where every shelf has a label saying "surnames Ka to Ku". Looking for "Kumar", you walk past every shelf that cannot contain it. You never open those shelves at all.

COMPUTE AND COST

4. Virtual Warehouse, Cache, Resource Monitor

Where the money goes, and how to stop it going there.

Virtual warehouse

A warehouse is compute — it does not store anything. Sizes go XS, S, M, L, XL and upward, and each step doubles both the compute power and the credits per hour. An XS burns 1 credit/hour, S burns 2, M burns 4, and so on.

CREATING A SENSIBLE WAREHOUSECREATE WAREHOUSE WH_TRANSFORM WITH
  WAREHOUSE_SIZE = 'MEDIUM'
  AUTO_SUSPEND   = 60          -- seconds of idleness before it sleeps
  AUTO_RESUME    = TRUE        -- wakes on the next query
  INITIALLY_SUSPENDED = TRUE
  MIN_CLUSTER_COUNT = 1        -- multi-cluster: Enterprise edition
  MAX_CLUSTER_COUNT = 3
  SCALING_POLICY = 'STANDARD';

Scale up — a bigger size

Fixes one slow, heavy query: large joins, big sorts, queries spilling to disk. More power per query.

Scale out — more clusters

Fixes many users queuing at once. Extra clusters start automatically and shut down when the queue clears. More queries at the same time, same power each.

Scale up or scale out?

One query is slow → scale up. Fifty people are waiting → scale out. Interviewers ask this exact question, and answering it backwards is a common trip-up.

Cache — the three types

CacheWhere it livesBehaviour
Result cacheCloud services layerHolds query results for 24 hours. If the same query text runs on unchanged data, the result comes back instantly and costs no compute.
Local disk cacheOn the warehouse's SSDsHolds micro-partitions the warehouse recently read. Lost when the warehouse suspends.
Metadata cacheCloud services layerStatistics like row counts and min/max. This is why SELECT COUNT(*) returns without starting a warehouse.
The classic follow-up: why did my second run get slower?

Because the warehouse suspended between runs and the local disk cache was thrown away. That is also the honest trade-off of aggressive auto-suspend — you save credits but lose warm cache. Sixty seconds is the usual compromise.

Resource monitor

A credit budget with automatic actions. Set it at account level or per warehouse.

SPEND CONTROLCREATE RESOURCE MONITOR RM_MONTHLY WITH
  CREDIT_QUOTA = 500
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 90 PERCENT DO SUSPEND            -- lets running queries finish
    ON 100 PERCENT DO SUSPEND_IMMEDIATE; -- kills running queries

ALTER WAREHOUSE WH_TRANSFORM SET RESOURCE_MONITOR = RM_MONTHLY;

Only ACCOUNTADMIN can create these. SUSPEND is polite, SUSPEND_IMMEDIATE is not — know that difference.

Fail-safe explained simply

Seven extra days after Time Travel expires where only Snowflake support can recover your data. You cannot query it, you cannot switch it off on permanent tables, and you do pay storage for it. That is exactly why staging tables are made transient.

CREATING OBJECTSCREATE DATABASE SALES_DB;
CREATE SCHEMA SALES_DB.RAW;

CREATE TABLE SALES_DB.RAW.ORDERS (
  order_id    NUMBER AUTOINCREMENT,
  cust_id     NUMBER,
  order_date  DATE,
  amount      NUMBER(12,2),
  load_ts     TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
) DATA_RETENTION_TIME_IN_DAYS = 7;

CREATE TRANSIENT TABLE SALES_DB.STG.ORDERS_STG LIKE SALES_DB.RAW.ORDERS;
CREATE TABLE ORDERS_BACKUP AS SELECT * FROM ORDERS;   -- CTAS
Constraints are documentation, not enforcement

Snowflake accepts PRIMARY KEY and FOREIGN KEY declarations but does not enforce them — only NOT NULL is enforced. They exist for the optimiser and for tools reading your metadata. Say this in an interview and it lands well, because many candidates assume otherwise.

DATA PROTECTION

6. Time Travel & Zero Copy Cloning

Two features that exist because of how micro-partitions work.

Time Travel

Every change writes new micro-partitions instead of overwriting old ones. The old ones stay for the retention period, so Snowflake can show you the table as it was at any moment inside that window. Standard edition gives 1 day; Enterprise allows up to 90 on permanent tables.

THREE WAYS TO GO BACKSELECT * FROM orders AT (OFFSET => -600);                      -- 10 minutes ago
SELECT * FROM orders AT (TIMESTAMP => '2026-09-01 09:00:00'::TIMESTAMP_LTZ);
SELECT * FROM orders BEFORE (STATEMENT => '01a2b3c4-...');       -- just before that query

-- restore a table to a point in time
CREATE OR REPLACE TABLE orders CLONE orders BEFORE (STATEMENT => '<query_id>');

-- and if the whole object was dropped
UNDROP TABLE orders;
UNDROP SCHEMA raw;
UNDROP DATABASE sales_db;
Picture

Time Travel is CCTV footage of your table. You cannot stop the accident, but you can rewind and see exactly what the data looked like at 1:59 pm — and copy that version back.

Zero copy cloning

A clone copies metadata only. Both tables point at the same micro-partitions, so the clone is instant and costs no extra storage. Storage only grows when one side changes — then just the changed partitions are written.

CLONINGCREATE DATABASE UAT_DB CLONE PROD_DB;                -- whole environment, seconds
CREATE TABLE orders_test CLONE orders;
CREATE TABLE orders_yesterday CLONE orders AT (OFFSET => -86400);  -- clone + time travel
Where you actually use these two together

Before every production deployment, clone the database. If the release goes wrong, restore from the clone. It costs nothing while nothing changes, and it converts a frightening deployment into a reversible one. That answer covers rollback strategy in a CI/CD question too.

What a clone does not carry

Clones are independent after creation — changes on one side never affect the other. External tables and internal named stages inside a cloned database do not bring their files along, and pipes need care. Also, cloning does not copy privileges granted on the source's child objects unless you ask for it.

SEMI-STRUCTURED DATA

7. JSON & XML — Semi-structured Data

Snowflake stores nested data natively. No shredding, no separate NoSQL store.

The three special types

  • VARIANT — holds any semi-structured value, up to 16 MB compressed per row.
  • OBJECT — a key-value map.
  • ARRAY — an ordered list.
READING JSONCREATE TABLE raw_orders (payload VARIANT);

-- colon walks into keys, dot works too, [] indexes arrays, :: casts
SELECT payload:order_id::STRING        AS order_id,
       payload:customer.name::STRING    AS cust_name,
       payload:items[0].price::NUMBER   AS first_price
FROM raw_orders;
FLATTEN — TURNING AN ARRAY INTO ROWSSELECT r.payload:order_id::STRING AS order_id,
       f.value:sku::STRING         AS sku,
       f.value:qty::INT            AS qty,
       f.index                     AS line_no
FROM raw_orders r,
LATERAL FLATTEN(input => r.payload:items) f;
FLATTEN in one image

A lunchbox with four compartments arrives as one row. FLATTEN opens it and lays each item on the table as its own row, keeping a label that says which lunchbox it came from.

Loading JSON files

FILE FORMAT AND COPYCREATE FILE FORMAT ff_json TYPE=JSON STRIP_OUTER_ARRAY=TRUE;

COPY INTO raw_orders
FROM @my_stage/orders/
FILE_FORMAT = ff_json;
-- STRIP_OUTER_ARRAY splits a top-level [ {...}, {...} ] into one row per object

XML

XML also loads into a VARIANT column, using TYPE=XML. Navigation is clumsier than JSON because you deal with tags and attributes.

XML NAVIGATIONCREATE FILE FORMAT ff_xml TYPE=XML STRIP_OUTER_ELEMENT=TRUE;

SELECT XMLGET(payload, 'customer'):"$"::STRING       AS customer,
       GET(XMLGET(payload, 'order'), '@id')::STRING AS order_id
FROM raw_xml;
-- XMLGET picks a child element; "$" is its text; '@x' is an attribute
The design question behind this topic

Load semi-structured data into VARIANT in the RAW layer exactly as it arrived, then flatten it into proper typed columns in staging. Keeping the original means a changed source schema never loses data — you just re-run the flattening.

How files actually get into tables — the most practical topic in the course.

Stage types

External stage@ext_stagePoints at S3, Azure Blob or GCS. What real pipelines use.
EXTERNAL STAGE VIA STORAGE INTEGRATION (THE SECURE WAY)CREATE STORAGE INTEGRATION S3_INT
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/snowflake-role'
  ENABLED = TRUE
  STORAGE_ALLOWED_LOCATIONS = ('s3://my-bucket/data/');

  URL = 's3://my-bucket/data/'
  STORAGE_INTEGRATION = S3_INT
  FILE_FORMAT = ff_csv;

LIST @ext_stage;                    -- see what files are there
SELECT $1, $2, $3 FROM @ext_stage LIMIT 10;   -- peek before loading
Why storage integration and not keys

A storage integration uses a cloud IAM role, so no access key or secret ever sits in your SQL or your Git repo. Interviewers like this answer because it is a security decision, not just syntax.

File format

THE OPTIONS THAT SAVE YOUCREATE FILE FORMAT ff_csv
  TYPE = CSV
  FIELD_DELIMITER = ','
  SKIP_HEADER = 1
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'      -- handles commas inside quotes
  NULL_IF = ('', 'NULL', '\\N')
  EMPTY_FIELD_AS_NULL = TRUE
  DATE_FORMAT = 'YYYY-MM-DD'
  ERROR_ON_COLUMN_COUNT_MISMATCH = FALSE
  COMPRESSION = AUTO;                       -- gz, bz2 detected automatically

COPY INTO — loading

LOAD, WITH THE OPTIONS THAT MATTERCOPY INTO orders
FROM @ext_stage/orders/
FILE_FORMAT = ff_csv
PATTERN = '.*orders_2026.*[.]csv'
ON_ERROR = 'CONTINUE'          -- ABORT_STATEMENT (default) | SKIP_FILE | CONTINUE
PURGE = FALSE                     -- TRUE deletes source files after success
FORCE = FALSE;                    -- TRUE re-loads files already loaded

-- transform while loading: select from the stage, reorder, cast, add columns
COPY INTO orders (order_id, amount, load_ts)
FROM (SELECT $1::NUMBER, $3::NUMBER, CURRENT_TIMESTAMP() FROM @ext_stage/orders/)
FILE_FORMAT = ff_csv;

-- validate first, load nothing
COPY INTO orders FROM @ext_stage/orders/ FILE_FORMAT=ff_csv VALIDATION_MODE=RETURN_ERRORS;
The load-history rule that trips people up

COPY remembers every filename it has loaded for 64 days and refuses to load the same file again. That is a protection, not a bug. If you genuinely need a reload, use FORCE = TRUE — and be sure you are not about to duplicate rows.

Unloading, and local files

OUT, AND IN FROM YOUR LAPTOPCOPY INTO @ext_stage/export/orders_
FROM (SELECT * FROM orders WHERE order_date >= '2026-01-01')
FILE_FORMAT = (TYPE=CSV COMPRESSION=GZIP)
HEADER = TRUE
SINGLE = FALSE
MAX_FILE_SIZE = 50000000;

-- SnowSQL only, not the web UI
PUT file:///home/rahul/data/orders.csv @my_stage AUTO_COMPRESS=TRUE;
GET @my_stage/orders.csv.gz file:///home/rahul/download/;

Two monitoring views worth knowing: INFORMATION_SCHEMA.COPY_HISTORY and SNOWFLAKE.ACCOUNT_USAGE.LOAD_HISTORY. When someone says "the file did not load", these answer it in one query. Also VALIDATE(orders, JOB_ID => '_last') shows the rows a load rejected.

CONTINUOUS LOADING

9. Snowpipe & External Tables

Continuous loading, and querying files you never load at all.

Snowpipe

A pipe is a COPY statement that runs itself when a file arrives. Auto-ingest works through a cloud notification — SQS on AWS, Event Grid on Azure — so latency is usually under a minute. It runs on Snowflake-managed serverless compute, so no warehouse of yours is billed.

PIPE, AND THE COMMAND YOU WILL ACTUALLY NEEDCREATE PIPE raw_db.mf.pipe_orders
  AUTO_INGEST = TRUE
AS
  COPY INTO raw_db.mf.orders_raw
  FROM @ext_stage/orders/
  FILE_FORMAT = ff_csv;

SHOW PIPES;                                  -- grab notification_channel → put in S3 event config
SELECT SYSTEM$PIPE_STATUS('pipe_orders');      -- executionState, pendingFileCount
ALTER PIPE pipe_orders REFRESH;                -- pick up files missed while paused
SnowpipeBulk COPY
TriggerFile arrival eventYou run it, or a task does
ComputeSnowflake serverlessYour virtual warehouse
Best forSmall files arriving continuouslyLarge historical batches
BillingPer file plus compute secondsWarehouse time
Picture

Snowpipe is an automatic door: it opens the moment somebody arrives. Bulk COPY is a watchman who opens the gate when you tell him to. For a truckload of luggage, call the watchman.

External tables

An external table leaves data in cloud storage and queries it in place. Snowflake stores only metadata. Useful for data lakes, archives and anything you query rarely.

EXTERNAL TABLE WITH PARTITIONSCREATE EXTERNAL TABLE ext_orders (
  order_date DATE AS TO_DATE(SPLIT_PART(METADATA$FILENAME, '/', 3), 'YYYYMMDD'),
  order_id   NUMBER AS (VALUE:c1::NUMBER),
  amount     NUMBER AS (VALUE:c3::NUMBER)
)
PARTITION BY (order_date)
LOCATION = @ext_stage/orders/
FILE_FORMAT = ff_csv
AUTO_REFRESH = TRUE;
Be honest about the trade-off

External tables are slower than native tables — no micro-partitions, no clustering, weaker pruning. They save storage cost and suit cold data. If a table is queried daily by dashboards, load it properly instead. A materialised view over an external table is the middle path.

GOVERNANCE

10. Data Masking & Row Access Policy

Column-level and row-level security, both driven by the role that is asking.

Dynamic data masking

One policy, attached to a column. The same query returns different values depending on who runs it — no separate views, no duplicated tables.

MASKING POLICYCREATE MASKING POLICY mp_email AS (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('R_ADMIN', 'R_COMPLIANCE') THEN val
    WHEN CURRENT_ROLE() = 'R_ANALYST' THEN REGEXP_REPLACE(val, '.+@', '****@')
    ELSE '**MASKED**'
  END;

ALTER TABLE customers MODIFY COLUMN email SET MASKING POLICY mp_email;
ALTER TABLE customers MODIFY COLUMN email UNSET MASKING POLICY;

Row access policy

Same idea, but it decides which rows a role can see. The usual pattern is a mapping table of role to region, joined inside the policy.

ROW ACCESS POLICY WITH A MAPPING TABLECREATE ROW ACCESS POLICY rap_region AS (region STRING) RETURNS BOOLEAN ->
  CURRENT_ROLE() = 'R_ADMIN'
  OR EXISTS (
      SELECT 1 FROM sec.role_region_map m
       WHERE m.role_name = CURRENT_ROLE()
         AND m.region    = region);

ALTER TABLE sales ADD ROW ACCESS POLICY rap_region ON (region);
How the two combine

Row access policies run first and decide which rows come back; masking then decides what the columns look like. A South-region analyst sees only South rows, with the email column already masked. One table serves everybody, which is the whole point.

Pictures

Masking is an Aadhaar printout showing XXXX-1234 — the row is there, the value is hidden. A row access policy is the security guard at the gate who only lets your own department's files reach your desk.

Related governance features worth naming: object tagging (tag columns as PII, then attach a masking policy to the tag so it applies everywhere), and SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY for the audit trail of who read what.

NATIVE PIPELINES

11. Streams & Tasks

Change tracking and scheduling — together they are Snowflake's native pipeline engine.

Stream

A stream sits on a table and records an offset. Query it and you see the rows that changed since that offset, plus three metadata columns. Consuming the stream in a DML statement advances the offset — which is what makes processing exactly-once.

Metadata columnMeaning
METADATA$ACTIONINSERT or DELETE
METADATA$ISUPDATETRUE when the pair of rows represents an update
METADATA$ROW_IDStable identifier for the row
STREAM TYPESCREATE STREAM str_orders ON TABLE raw.orders;                          -- standard: all DML
CREATE STREAM str_ins ON TABLE raw.orders APPEND_ONLY = TRUE;          -- inserts only, cheaper
CREATE STREAM str_ext ON EXTERNAL TABLE ext_orders INSERT_ONLY = TRUE;

SELECT SYSTEM$STREAM_HAS_DATA('str_orders');   -- TRUE / FALSE
Staleness — the question that separates readers from users

A stream becomes stale if it is not consumed within the source table's data retention period, and once stale it cannot be read. Keep retention sensible on tables that feed streams, and consume regularly. Also: reading a stream does not advance it — only using it in a DML does.

Task

A TASK DAGCREATE TASK t1_stage
  WAREHOUSE = wh_transform
  SCHEDULE  = 'USING CRON 0 2 * * * Asia/Kolkata'     -- or '15 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('str_orders')          -- skip = no compute = no cost
AS
  MERGE INTO stg.orders t
  USING str_orders s ON t.order_id = s.order_id
  WHEN MATCHED THEN UPDATE SET t.amount = s.amount
  WHEN NOT MATCHED THEN INSERT (order_id, amount) VALUES (s.order_id, s.amount);

CREATE TASK t2_fact WAREHOUSE=wh_transform AFTER t1_stage AS CALL sp_load_fact();
CREATE TASK t3_dq   WAREHOUSE=wh_transform AFTER t2_fact  AS CALL sp_reconcile();

-- resume children first, root LAST — a suspended root stops the whole DAG
ALTER TASK t3_dq RESUME; ALTER TASK t2_fact RESUME; ALTER TASK t1_stage RESUME;

SELECT * FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY()) ORDER BY scheduled_time DESC;
Three things to remember about tasks

A new task is created suspended — you must resume it. Only one root task per DAG, and a child cannot have two parents in the classic model. Serverless tasks (omit the warehouse and set USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE) let Snowflake size the compute for you.

Pictures

A stream is the WhatsApp unread badge — it shows what is new and clears when you act on it. A task DAG is a relay race, where the baton only passes if the previous runner finished.

PRESENTING DATA

12. Views & Dynamic Tables

Four ways to present data, each with a different cost and freshness trade-off.

ObjectStores data?FreshnessCost
Standard viewNo — runs the query each timeAlways currentCompute at query time
Secure viewNoAlways currentSlightly slower — optimiser hides internals
Materialised viewYesAuto-maintained by SnowflakeStorage plus background maintenance
Dynamic tableYesRefreshes to meet your target lagStorage plus refresh compute
VIEWSCREATE VIEW v_sales AS SELECT region, SUM(amount) amt FROM sales GROUP BY region;

-- secure view: hides the definition and blocks optimiser tricks that could leak rows
CREATE SECURE VIEW v_customer_sales AS
SELECT sale_month, region, total_sales FROM cur.monthly_summary;
GRANT SELECT ON VIEW v_customer_sales TO ROLE r_customer;

-- materialised view: single table only, no joins, limited aggregates
CREATE MATERIALIZED VIEW mv_daily AS
SELECT sale_date, region, SUM(amount) amt FROM sales GROUP BY 1,2;
Materialised view limits — asked often

One table only, no joins, no window functions, no ORDER BY, limited aggregate support, and Enterprise edition required. If you need joins with automatic refresh, that is exactly what a dynamic table is for.

Dynamic tables

You declare the result you want and a target lag. Snowflake works out how to refresh it — incrementally when it can, fully when it must — and chains dependent dynamic tables automatically. It replaces a lot of stream-plus-task plumbing.

DECLARATIVE PIPELINECREATE DYNAMIC TABLE dt_daily_sales
  TARGET_LAG = '30 minutes'          -- or 'DOWNSTREAM' to follow the consumer
  WAREHOUSE  = wh_transform
AS
SELECT s.sale_date, c.region, SUM(s.amount) AS total
FROM stg.sales s JOIN dim.customer c ON s.cust_id = c.cust_id
GROUP BY 1,2;

ALTER DYNAMIC TABLE dt_daily_sales REFRESH;    -- manual nudge
How to choose, in one line each

Small logic, always fresh → view. Sensitive data going outside → secure view. Repeated heavy aggregate on one table → materialised view. A multi-step transformation chain you would otherwise build with streams and tasks → dynamic tables.

SHARING AND PERFORMANCE

13. Data Sharing & Clustering

Giving data away without copying it, and making huge tables fast.

Secure data sharing

A share is metadata, not data. The consumer queries your micro-partitions directly using their own warehouse, so they pay the compute and you pay only your storage — once. There is no copy, no ETL, and no staleness.

PROVIDER SIDECREATE SHARE sales_share;
GRANT USAGE ON DATABASE rpt_db TO SHARE sales_share;
GRANT USAGE ON SCHEMA rpt_db.public TO SHARE sales_share;
GRANT SELECT ON VIEW rpt_db.public.v_customer_sales TO SHARE sales_share;
ALTER SHARE sales_share ADD ACCOUNTS = ('CUSTOMER_ACCT');
CONSUMER SIDECREATE DATABASE shared_sales FROM SHARE provider_acct.sales_share;
SELECT * FROM shared_sales.public.v_customer_sales;   -- read-only, always live
Two rules and one workaround

Shares are read-only, and normally both accounts must be on the same cloud and region — otherwise you set up replication first. If the customer has no Snowflake account, create a reader account: you provision and pay for it, they just query.

Clustering

Snowflake orders data naturally as it loads. On very large tables that natural order stops matching how people filter, pruning degrades, and queries scan too much. A clustering key tells Snowflake to keep the table sorted on those columns in the background.

CHECK BEFORE YOU CLUSTERSELECT SYSTEM$CLUSTERING_INFORMATION('sales', '(sale_date, region)');
-- look at average_overlaps and average_depth; lower is better

ALTER TABLE sales CLUSTER BY (sale_date, region);
ALTER TABLE sales DROP CLUSTERING KEY;
Clustering is not free, and not always right

Automatic reclustering consumes credits continuously. It pays off on tables in the multi-terabyte range that are queried often on the same columns. On a table of a few gigabytes it usually costs more than it saves. Choose low-to-medium cardinality columns that appear in WHERE and JOIN clauses, order them from lowest to highest cardinality, and keep the key to three or four columns.

Related: search optimisation service is the better choice for point lookups on high-cardinality columns — ALTER TABLE t ADD SEARCH OPTIMIZATION; — while clustering suits range scans.

RETURNS STRING

  row_count INTEGER DEFAULT 0;

Owner's rights versus caller's rights

Models and the ref() function

A model is one SQL file producing one object. The magic is ref(): it points at another model, and from those references dbt builds the dependency graph and decides the run order for you. You never write the order by hand.

models/staging/stg_orders.sql{{ config(materialized='view') }}

    order_id::NUMBER            AS order_id,
    customer_id::NUMBER         AS customer_id,

SELECT o.order_id, o.order_date, c.region, o.amount
FROM {{ ref('stg_orders') }} o
JOIN {{ ref('dim_customer') }} c ON o.customer_id = c.customer_id

Why ref() is the whole point

Because dbt knows the graph, it can run models in the correct order in parallel, rebuild only what a change affects, and swap schemas between dev and prod without you editing a single query. Hardcode a table name instead of using ref() and you lose all three.

16. dbt Snapshots & Tests

History tracking, and the safety net that makes a pipeline trustworthy.

Snapshots — SCD Type 2, handled for you

Source systems overwrite. A snapshot captures the row before it changed, so you keep history with valid-from and valid-to columns. This is the same passport idea from dimension modelling, written in about ten lines.

snapshots/snap_customer.sql{% snapshot snap_customer %}
{{ config(
     target_schema='snapshots',
     unique_key='customer_id',
     strategy='check',
     check_cols=['name', 'city', 'segment']
) }}

SELECT * FROM {{ source('raw', 'customers') }}
{% endsnapshot %}
StrategyHow it detects changeUse when
timestampCompares an updated_at columnThe source has a reliable modified timestamp — cheaper and preferred
checkCompares the listed columns value by valueNo reliable timestamp exists

dbt adds dbt_valid_from, dbt_valid_to, dbt_scd_id and dbt_updated_at. Current rows carry a NULL dbt_valid_to.

Snapshots only see what is there when they run

If a value changes twice between two snapshot runs, the middle state is lost forever. Snapshot frequency is therefore a business decision, not a technical one — ask how much history the business actually needs before setting the schedule.

Tests

Two kinds. Generic tests are declared in YAML and reused everywhere; singular tests are SQL files that return failing rows. A test passes when it returns zero rows.

models/marts/schema.yml — GENERIC TESTSversion: 2
models:
  - name: fct_sales
    description: One row per order, joined to customer region.
    columns:
      - name: order_id
        description: Primary key from the source system.
        tests:
          - unique
          - not_null
      - name: region
        tests:
          - accepted_values:
              values: ['North', 'South', 'East', 'West']
      - name: customer_id
        tests:
          - relationships:
              to: ref('dim_customer')
              field: customer_id
tests/assert_no_negative_amounts.sql — SINGULAR TEST-- passes only if this returns nothing
SELECT order_id, amount
FROM {{ ref('fct_sales') }}
WHERE amount < 0

The four built-in generic tests — unique, not_null, accepted_values, relationships — cover most real problems. Add dbt-utils for things like equal_rowcount and expression_is_true. Set severity: warn when a failure should be visible but not stop the pipeline.

Why this is your best dbt talking point

Tests are how a pipeline earns trust. Say that you test primary keys for uniqueness and nullness on every model, referential integrity between facts and dimensions, and business rules as singular tests — and that dbt build stops downstream models when a test fails, so bad data never reaches a dashboard.

18. Azure Data Factory & AWS Integration

Getting data from source systems into cloud storage, which is where Snowflake picks it up.

Where these tools sit

Source DB / SaaS / files→ ADF or Glue (EL)→ S3 / Blob→ Snowflake (T)

ADF and AWS Glue handle extract and load. Transformation belongs inside Snowflake, using SQL or dbt, because that is where the compute is cheap and elastic. Doing heavy transformation in ADF data flows is a common but expensive design mistake.

ADF building blocks

ComponentWhat it is
Linked serviceA connection — to SQL Server, Blob storage, Snowflake. Credentials should come from Key Vault.
DatasetA pointer to the actual data: a table, a folder, a file pattern.
ActivityOne unit of work: Copy, Lookup, ForEach, Stored Procedure, Data Flow.
PipelineActivities wired together with dependencies and error paths.
TriggerSchedule, tumbling window, or storage event.
Integration runtimeThe compute. Self-hosted IR is what reaches on-premises SQL Server.

The metadata-driven pattern worth describing

  1. A control table lists every source table with its watermark column and last-loaded value.
  2. A Lookup activity reads that control table.
  3. A ForEach activity loops over the rows, running a Copy activity per table with parameters.
  4. Copy pulls rows greater than the watermark and writes Parquet to Blob or S3, partitioned by date.
  5. A Stored Procedure activity updates the watermark only after a successful copy.
  6. Snowpipe or a COPY task picks the files up from there.
Why this pattern impresses

One pipeline handles two hundred tables. Adding a table means inserting a row in the control table — no new pipeline, no redeployment. Say this instead of "I built a copy activity" and the conversation changes level.

AWS side

  • S3 — the landing zone. Organise as s3://bucket/system/table/yyyymmdd/.
  • IAM role and trust policy — what a Snowflake storage integration assumes. No keys anywhere.
  • SQS notification — what makes Snowpipe auto-ingest fire on file arrival.
  • Lambda / Glue — event-driven conversion and cleanup jobs before loading.
  • Secrets Manager — where credentials live if a job needs them.

DESIGN PATTERN

19. Medallion Architecture

The layered design almost every Snowflake project uses. Bronze, Silver, Gold.

Medallion architecture is a way of organising a data platform into layers, where data gets cleaner and more business-ready as it moves through each one. Nothing is deleted along the way, so you can always go back and rebuild a later layer from an earlier one. The name comes from medal metals: bronze is raw, silver is refined, gold is the finished product.

Source→ Bronze / RAW→ Silver / STAGING→ Gold / CURATED→ Reports

What each layer is for

LayerWhat it holdsRules that define it
Bronze
(RAW)		 Data exactly as it arrived — every column, every row, including bad ones. Never edit it. No business logic. Keep the source file name and load timestamp for lineage. Semi-structured data stays in VARIANT here. This layer is your ability to replay history.
Silver
(STAGING)		 Cleaned, typed, deduplicated data. One row per real-world event or entity. Cast data types, trim and standardise text, handle nulls, deduplicate, route rejects to an error table, apply light conformance across sources. Still close to source shape — not yet modelled for the business.
Gold
(CURATED / MART)		 Business-ready facts and dimensions, aggregates, KPIs. Star schema, SCD2 dimensions, joins across sources, business rules applied, named the way the business speaks. This is what dashboards and shares point at.
The one rule that makes the whole pattern work

Each layer reads only from the layer directly above it. A gold table never reads bronze directly. That single discipline is what lets you fix a cleaning bug in silver and rebuild gold, without touching ingestion or going back to the source system.

Building it in Snowflake

DATABASES, SCHEMAS AND THE RIGHT TABLE TYPE PER LAYERCREATE DATABASE RAW_DB;    -- bronze: permanent, keeps history, cheap to replay from
CREATE DATABASE STG_DB;    -- silver: transient tables, no fail-safe cost, fully rebuildable
CREATE DATABASE CUR_DB;    -- gold: permanent, longer Time Travel, this is the asset
CREATE DATABASE RPT_DB;    -- secure views and shares for consumers

-- bronze keeps lineage columns
CREATE TABLE RAW_DB.SALES.ORDERS_RAW (
  payload      VARIANT,
  src_file     STRING DEFAULT METADATA$FILENAME,
  load_ts      TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
);

-- silver is transient: it can always be rebuilt from bronze
CREATE TRANSIENT TABLE STG_DB.SALES.ORDERS_CLEAN (
  order_id NUMBER, cust_id NUMBER, order_date DATE, amount NUMBER(12,2)
);

-- gold gets the protection
ALTER TABLE CUR_DB.SALES.FACT_SALES SET DATA_RETENTION_TIME_IN_DAYS = 7;
MOVING BETWEEN LAYERS WITH STREAMS AND TASKS-- bronze → silver: dedupe and type on the way
CREATE STREAM str_orders ON TABLE RAW_DB.SALES.ORDERS_RAW;

CREATE TASK t1_silver WAREHOUSE=wh_transform
  SCHEDULE='15 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('str_orders')
AS
  INSERT INTO STG_DB.SALES.ORDERS_CLEAN
  SELECT payload:order_id::NUMBER, payload:cust_id::NUMBER,
         payload:order_date::DATE, payload:amount::NUMBER(12,2)
  FROM str_orders
  WHERE METADATA$ACTION = 'INSERT'
  QUALIFY ROW_NUMBER() OVER (PARTITION BY payload:order_id ORDER BY load_ts DESC) = 1;

-- silver → gold: business modelling
CREATE TASK t2_gold WAREHOUSE=wh_transform AFTER t1_silver
AS CALL CUR_DB.SALES.SP_LOAD_FACT_SALES();

The same pattern in dbt

dbt's recommended folder structure is medallion by another name, which is why the two are almost always taught together.

Medallion layerdbt folderTypical materialisation
BronzeSources, declared in sources.ymlLoaded by Snowpipe or COPY, not by dbt
Silvermodels/staging/ then models/intermediate/view, or ephemeral for intermediates
Goldmodels/marts/table or incremental
Picture for the three layers

Vegetables from the market. Bronze is the sack as it came, mud still on it — you keep it because you may need to check what you were sold. Silver is washed and chopped. Gold is the dish on the table, ready to serve. You never cook straight from the muddy sack, and you never throw the sack away until the meal is served.

Why interviewers like this question

  • Replayability. Keeping bronze untouched means any downstream bug is fixable without re-extracting from the source — which often is not even possible.
  • Cost control. Silver as transient tables removes fail-safe storage on data that is fully rebuildable.
  • Blast radius. A bad transformation damages one layer, not the platform.
  • Clear ownership. Ingestion owns bronze, data engineers own silver, analytics engineers own gold. The boundaries are also team boundaries.
  • Security. Masking and row access policies belong in gold and the reporting views, where business users actually read data.
Where teams get it wrong

Putting business logic in bronze, which destroys replayability. Letting reports read silver directly, so definitions drift. Creating so many sub-layers that nobody can trace a number. And making silver permanent with long retention, quietly paying fail-safe on data that could be rebuilt in ten minutes.

If someone calls it something else

You will hear the same idea named multi-hop architecture, or simply raw–staging–curated. Lakehouse writing tends to use bronze, silver and gold; classic warehousing says landing, staging and presentation. If a job description uses one vocabulary, use theirs — the design underneath is identical.

Project A — AWS to Snowflake batch pipeline

TEST YOURSELF

23. Self Check

Answer out loud before opening. If you cannot say it aloud, you have not learned it yet.

Why can two teams query the same table without slowing each other down?

Storage is central and shared, compute is separate. Each team uses its own virtual warehouse, and warehouses do not share resources — so a heavy finance query cannot delay the loading pipeline.

Your query got slower on the second run. Give two possible reasons.

The warehouse suspended in between, so the local disk cache was lost. Or the underlying data changed, which invalidates the result cache and forces a real scan.

What is partition pruning and what kills it?

Snowflake reads micro-partition metadata and skips partitions that cannot match your filter. Wrapping the filtered column in a function, filtering on a column unrelated to the natural load order, or a badly clustered large table all reduce pruning.

An analyst cannot see a table created this morning, though you granted SELECT last week. Why?

The grant was ON ALL TABLES, which only covered tables existing at that moment. New tables need GRANT SELECT ON FUTURE TABLES IN SCHEMA.

Someone deleted rows an hour ago. Walk through recovery.

Find the query id in query history, read the table with BEFORE (STATEMENT => ...) to confirm, then CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...). If the whole table was dropped, UNDROP TABLE. All of this only works inside the retention window.

You cloned a 5 TB database for testing. What does it cost on day one, and later?

Nothing on day one — only metadata is copied, and both point at the same micro-partitions. Storage grows only as either side changes, and only for the changed partitions.

Why did COPY INTO load nothing, though the file is clearly in the stage?

Most likely the file was already loaded — COPY keeps load history for 64 days and skips duplicates. Check COPY_HISTORY. Other candidates: the PATTERN did not match, or a stale file list. FORCE = TRUE reloads, but confirm you will not duplicate rows.

What makes a stream go stale, and how do you avoid it?

Not consuming it within the source table's data retention period. Keep retention adequate on tables that feed streams, and consume regularly with a task. Remember that only a DML consuming the stream advances its offset — a plain SELECT does not.

Why does the WHEN clause on a task save money?

WHEN SYSTEM$STREAM_HAS_DATA(...) makes the task skip entirely if there is nothing new. A skipped task never resumes the warehouse, so no credits are consumed on empty runs.

Your task DAG did not run at all. First thing to check?

Whether the root task is resumed — tasks are created suspended, and a suspended root stops the whole chain. Then check TASK_HISTORY for the scheduled state and any error.

Explain the difference between masking and a row access policy.

Masking changes what a column looks like for a given role. A row access policy decides which rows come back at all. Row filtering runs first, then masking is applied to the surviving rows.

The customer has no Snowflake account. How do you share data?

Create a reader account. You provision and pay for it, they log in and query your shared views read-only. Otherwise a direct share needs both accounts on the same cloud and region, or replication first.

When would you refuse to add a clustering key?

On a small or moderately sized table, on a table nobody filters consistently, or on one that is rewritten frequently — automatic reclustering would burn more credits than the queries save.

What does dbt's ref() give you that a hardcoded table name does not?

The dependency graph. From it dbt derives run order, parallelism, selective rebuilds with + selectors, and environment switching between dev and prod schemas.

How does a dbt incremental model avoid reprocessing everything?

On the first run it builds fully. Afterwards the is_incremental() block adds a filter — usually rows newer than the maximum date already in {{ this }} — and dbt merges them using the unique key. --full-refresh rebuilds from scratch.

Give three dbt tests you would put on every fact table.

Unique and not null on the primary key, a relationships test to each dimension, and an accepted-values or expression test on a business-critical column such as status or amount.

Where should transformation happen in an ADF plus Snowflake design, and why?

In Snowflake. ADF extracts and lands files; Snowflake compute is elastic, cheaper for set-based work, and keeps the logic in SQL where it can be tested and version-controlled.

Why keep a bronze layer at all, when silver already has clean data?

Replayability. If a cleaning rule turns out to be wrong six months later, you rebuild silver and gold from bronze rather than re-extracting from a source system that may no longer hold that history. Bronze is also your audit trail of what the source actually sent.

Name one good and one poor use of Cortex LLM functions.

Good: classifying or summarising a text column, or anomaly detection on load metrics. Poor: calling COMPLETE inside a row-level transformation over millions of rows — token cost makes that indefensible.
